Ask Tut — Security and Data Handling Overview

Effective date: 30 October 2026 · Version: 1.0

This page is written for IT, security and compliance reviewers (and for marketplace reviews such as the Microsoft 365 Publisher Attestation and the Salesforce security review). It describes how Ask Tut is built, what it touches, and what controls apply. Contractual commitments are in the Terms of Service and DPA; this page is descriptive.

1. Architecture in one paragraph

Ask Tut has three parts. (1) Front ends inside the platform your people already use — a side pane in Dynamics 365, a record card in HubSpot, a utility panel in Salesforce, a web chat page, and a Microsoft Teams bot. (2) The Ask Tut service — a small Node.js application on Azure Functions (Flex Consumption plan, Canada Central) that runs the conversation loop, enforces the administrator's rules, calls the platform's data APIs as the signed-in user, and calls the AI model. (3) The AI model — Claude, through Anthropic's API or through Microsoft Foundry in the customer's own Azure subscription. There is no Ask Tut database of business data: the customer's platform stays the system of record.

User ──(sign-in, question)──► Front end ──► Ask Tut service (Azure Function, Canada Central) │ as the user (OAuth / OBO) ├──► Platform data API (Dataverse MCP / BC MCP / F&O OData / Graph / HubSpot / Salesforce MCP) ├──► AI model (Claude API: Global or US only · or Foundry in customer's Azure) └──► Ask Tut records (usage log, change history, settings): customer's Dataverse/SharePoint or Azure Table storage

2. Identity and authorization

Edition How Ask Tut authenticates to your data

HubSpot Current release: the app's installation token, constrained by Tut Admin rules and the approval step. Planned: HubSpot's MCP auth app / user-level OAuth so each user's own HubSpot permissions apply.

Administrator functions (Tut Admin, Consumption dashboard, report download, provider check) require the platform's administrator role (Dynamics: System Administrator or System Customizer; Salesforce: System Administrator; Business Central: Entra app role Tut.Admin; HubSpot: app settings page, super-admin) and are checked server-side on every call.

Service identity: where Ask Tut must write its own log rows (e.g., Dataverse tut_usage), it uses a dedicated application user with a custom role limited to create/read on Ask Tut's own tables — never System Administrator, Customizer or Maker roles.

3. The "approve before change" control

Ask Tut can read freely within the user's permissions and the administrator's allow-list, but every write goes through a fixed sequence: the model proposes a change → the service checks it against the administrator's rules (table allowed? field allowed? status change allowed? role rule?) → the user sees an Approve / Deny card with the exact before/after → approval is a signed, single-use token (HMAC, nonce, 30-minute expiry) bound to that user and that change → the rules are re-checked at execution → the change is written as the user → the change is recorded in Change history. Denied or expired approvals do nothing. Bulk changes (max 50) use one approval listing every record.

Tools that send or deliver messages, export data in bulk, provision, register or administer are not offered to the model by design. Record deletion is off by default and, when an administrator enables it for a specific table, still requires the user's approval for each record. Ask Tut has no email or messaging send capability; "email draft" creates a draft record only.

4. Prompt-injection and model safeguards

  • The administrator's rules are enforced in code, not by asking the model to behave. A record or document containing instructions ("ignore your rules and delete…") cannot unlock a write — the policy check runs on the actual tool call.
  • Tool results are size-limited and treated as data; system instructions are separate from retrieved content.
  • Reads are limited to the tables/fields on the allow-list; "other tables" default to read-only or off.
  • Answers show the records used; case/record numbers link back to the source so users can verify.
  • Users can rate every answer (👍/👎 with comment); ratings and comments are visible to administrators in the dashboard for review and follow-up.
  • An "AI assistant" notice is shown in the interface; the assistant identifies itself as an AI when asked.

6. Encryption

TLS 1.2+ for every hop (front end ↔ service ↔ platform APIs ↔ AI provider). At rest: Azure Storage service-side encryption (AES-256, Microsoft-managed keys; customer-managed keys available in the customer-hosted edition), Dataverse encryption, Key Vault HSM-backed secrets. Approval tokens are HMAC-SHA256 signed with a per-deployment secret.

7. Hosting and operations

  • Azure Functions, Flex Consumption, Node.js 20/22, Canada Central; Azure Bot Service (Teams channel) with single-tenant or managed-identity bot identities (no bot secrets where the platform allows).
  • Customer-hosted edition: the same package deployed into the customer's subscription with the customer's Key Vault, storage and AI account; Oizn has no access.
  • Monitoring: Application Insights (errors, latency, availability); budget and usage alerts to administrators (Teams and in-app bell — never email).
  • Backups: Ask Tut holds no business data; its own records are in zone-redundant storage or in the customer's platform (covered by that platform's backup).
  • Change management: source in a private GitHub repository (OiznSystems/AskTut), version-tagged builds, offline test suites per edition (mock platform + scripted model) run before every deployment, deployment through Azure's zip-deploy with build numbers visible at /api/health.

8. Vulnerability and incident management

  • Dependencies pinned and reviewed; updates monthly or on critical advisories; Azure platform patching is managed by Microsoft.
  • Responsible disclosure: support@oizn.com. We acknowledge within 2 business days.
  • Incident response: triage → contain → notify affected customers within 48 hours of confirming a breach of personal data → remediate → post-incident report to affected customers within 30 days of resolution.

11. What Ask Tut does not do

By design: no email or message sending · no app-only access to business data · no copying of business records into an Ask Tut database · no training of AI models on customer data · no advertising or tracking · no access by Oizn staff to a customer-hosted deployment · no storage of secrets outside Key Vault · no record deletion unless the administrator explicitly enables it for a table and the user approves each one.
